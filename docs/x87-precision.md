# x87 precision and math helpers

The original game was compiled for the x87 floating point unit, and a surprising amount of its visible behaviour depends on how that unit rounds. Arithmetic is done in an 80-bit register and rounded to float only when a value is stored. The control word changes between the game tick and the render window, sine and arc functions come from the CPU instruction set or from the Microsoft C runtime rather than from a portable library, float-to-integer casts have unusual corner cases, and trace hits are sorted with the runtime's own `qsort`. The port reproduces all of these with a small exact model of an x87 register instead of plain C# float arithmetic, because per-step float rounding differs by one unit in the last place, and that is enough to flip a script branch or move a particle.

## Precision control: two windows

- **Game tick: 64-bit mantissa.** `appEnableFastMath(0)` leaves the control word at `0x037F`: precision control 64, round to nearest, all exceptions masked. A product of two floats is exact, sums round to a 64-bit mantissa, and the value rounds a second time to 24 bits on the store (`fstp dword`). The double rounding is what the CPU does, not an approximation. (port: `X87Ext.Round64`, [`X87Ext.cs`](../HP1.Core/Runtime/Native/X87Ext.cs); exec natives such as vector size, dot and cross in [`UENativesX87.cs`](../HP1.Core/Runtime/VM/UENativesX87.cs))
- **Render window: 24-bit mantissa.** `URender::PreRender` (Render.dll, around `0x10b01375`) calls `appEnableFastMath(1)` and `PostRender` calls `appEnableFastMath(0)`; the control word inside is `0x007F`, precision control 24. `UGameEngine::Draw` (Engine `0x1039fe40`, `0x1039feba`, `0x103a0006`) runs PreRender, `DrawWorld` and then PostRender. Every multiply, add, subtract, divide and square root rounds the register to a 24-bit mantissa; the exponent stays the register's 15 bits. Script that runs in that window (HUD, console) and `ActorShadow.Update` also run at PC24, so the same native body gives different bits inside and outside. (port: `X87Ext.Round24`; `UEWorldFrameProducer.FastMathWindow`)
- Typical consequence in other notes: surface panning, particle emission and occlusion arithmetic all assume PC24 (see [particles.md](particles.md), [procedural-textures.md](procedural-textures.md)).
- A model detail kept on purpose: a stored negative zero or NaN is observable (sign bit tests, `1/x`, `FastLineCheck` side from the sign of a stored float), so `X87Ext` carries the sign of zero, NaN payloads and the "real indefinite" `0xFFC00000` exactly as the FPU does with all exceptions masked.

## Sine, cosine, arc tangent, square root

- Game code calls `appSin` (Core `0x101035df` to `0x101260a0`: bare `fsin`), `appCos` (`0x101260b0`: `fcos`), `appAtan2` (`0x10102ab8` to `0x101260f0`: `fpatan`) and `appSqrt` (`0x10126100`: `fsqrt`). There is no library function behind them.
- Model chosen by the author (2026-10-30, record D-71): `fsin`, `fcos` and `fpatan` return the exact value **correctly rounded to the 64-bit mantissa**, whatever the precision control. Large arguments are first reduced with the x87's own value of pi/2 to 66 bits (the Intel manual's constant), not the true pi/2; the repo measured that the true-pi/2 reduction is already 2 ulps off at about -pi. Arguments of magnitude 2^63 and above leave the operand unchanged (the shipped helpers test no C2 flag). The result was checked against a table produced on real hardware (AMD Zen 2) with the genuine Microsoft runtime, 105622 rows: sine differed from the model by exactly 1 ulp of 80 bits on 840 of 61262 rows and arc tangent on 110 of 6792, and none differ after rounding to double or float. (port: [`UEX87Transcendental.cs`](../HP1.Core/Runtime/Native/UEX87Transcendental.cs), fast fixed-point path with an arbitrary-precision fallback)
- Open (D-71): which CPU's microcode is "the original" was an author decision; the consumers of these values are tested to be insensitive to a one-ulp nudge of the 80-bit result.

## acos from msvcrt 6.0

`appAcos` (Core `0x10101361` to `0x101260c0`) jumps to the C runtime's `_CIacos` through an import (`0x1025050c`). The game ships no runtime DLL, so the reference is msvcrt 6.00.8337.0 (`_CIacos` at `0x78028905`), chosen by the author on 2026-10-30; Wine's built-in version is a C reimplementation and is not used.
- Main path: `(1 + x)`, `(1 - x)`, multiplied, `fsqrt`, then `fpatan` with x, each step rounded at the **caller's** precision control (the routine rewrites the control word as `(cw & 0x300) | 0x7f`).
- The result is stored as a double and reloaded (`0x7802c277`), so it is rounded to 53 bits. This follows from the sticky precision flag: with the shipped control words `0x037F` and `0x007F` the `fpatan` is always inexact, so the double-rounding path is the one taken.
- `|x| = 1` and `|x| > 1` give 0 or NaN. `acos(-1)` is not modelled, because the result there depends on the caller's sticky flag; the only caller found (quaternion slerp, `|cos| < 1`) never passes it. (port: `CIacos` in `UEX87Transcendental.cs`; slerp itself ported bit for bit, D-71)
- `appExp` (Core `0x10126060`) is register-only and rounds at the caller's precision.

## Float to integer: `_ftol`

Float to int casts (`execFloatToInt` thunk `0x10102ee1`, `execFloatToByte` `0x10101a82`), time-to-ticks conversions and many renderer helpers call the runtime's `_ftol`: switch rounding to truncate, `fistp` to a 64-bit integer, return the low dword in `eax`.
- Truncation toward zero of the **unrounded** register value, not of a rounded float; `ULevel::Tick` multiplies the clamped delta by `TimeDilation` and `2^32` in the register and truncates (Engine `0x103b7062..0x103b70dc`).
- NaN, infinities and values at or beyond 2^63 give the "integer indefinite" `0x8000000000000000`, whose low dword is **zero**, not `int.MinValue`. For values between 2^31 and 2^63, `eax` is the low 32 bits of the 64-bit integer (wraps), no saturation. The gesture matcher's accuracy counter hits both cases and the results differ for odd counts of such terms (see [gestures.md](gestures.md)).
- `SubtlePulse` (Render.dll `0x10b06510`) feeds its sine argument through `_ftol` (truncation) while `Pulse` (`0x10b063d7`) uses `fistp` (round to nearest even): two neighbouring helpers with different rounding. (port: `UELevelRuntime.Ftol`; `UEGlobalRandoms.FtolLow`; `WorldFrame.cs` for the lighting effects)

## `qsort` from the C runtime

`appQsort` (Core) is a direct call to the runtime's `qsort`. The order of equal elements is deterministic but not stable, and it is visible to script because trace hits are sorted this way (`ULevel::MultiLineCheck`, `FindBase`, `TraceActors`). The reference is the `msvcrt.dll` of the compatibility layer the live 1.53 original was probed in (a newer msvcrt than the 6.0 used for acos above: it has `qsort_s`): `qsort` calls `qsort_s` with a comparator thunk (`0x100561c0` to `0x100561f0`). Algorithm: median-of-three partitioning with an explicit stack; a run shorter than 8 uses selection sort that moves the maximum to the end, so an equal element does not displace an earlier maximum. Checked against random arrays with ties. (port: [`MsvcQsort.cs`](../HP1.Core/Runtime/Native/MsvcQsort.cs))

## `rand()`

The game's `appRand`, `appFrand` and `appRandRange` all call the Visual C++ CRT `rand()`: state `s = s * 214013 + 2531011`, result `(s >> 16) & 0x7fff`. It is seeded with `time(NULL)` at Core start-up and reset to 1 for replay capture. `appFrand()` is `rand() * 1/32767` using a float constant (Core `0x1017ddb0`, bits `0x38000100`), so a draw of `0x7fff` gives exactly 1.0. `appFrand(min, max)` (Core `0x10126170`) is `fild rand; fmul C; fld max; fsub min; fmulp; fadd min`, one draw per call; `appRandRange(float, float)` (`0x101261a0`) multiplies by `max - min` first and by the scale after. Each operation rounds at the caller's precision, and the store rounds once more. `execVRand` builds its `2f - 1` component from the unrounded register value, which `NextFrandSt0` exposes. (port: [`MsvcRandom.cs`](../HP1.Core/Runtime/Native/MsvcRandom.cs))
- **Not original:** rendering uses its own random stream in the port; the original shares one stream between game and renderer. See [particles.md](particles.md).
- The renderer's global random tables (`FGlobalRandoms::Tick`, Render.dll `0x10b1d020`) run at PC24, with the time converted by `_ftol(Time * 35.0)`. (port: [`UEGlobalRandoms.cs`](../HP1.Core/Runtime/VM/UEGlobalRandoms.cs))
