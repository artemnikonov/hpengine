# Sprites and draw order

Three different orderings matter when the original draws a frame: the order of the frame's sprite list, the order `DrawFrame` hands sprites to `DrawActorSprite` on the Direct3D driver, and the order of faces inside one translucent mesh in `DrawLodMesh`. None of them is a plain back-to-front depth sort of actors, and the middle one is not by depth at all. This note records what the shipped Render.dll 1.53 does and where OpenHP1 follows it. Core decides the order; the frontend emits what it is given.

## Sprite list of a frame

- `FDynamicSprite::Setup` has a sprite branch for DrawType 1 and 7 (Render.dll 0x10b30e4b..0x10b3111d). It rejects an actor with no texture, computes depth `Z = ((dz*Z.z + dy*Z.y) + dx*Z.x) - SpriteProjForward` (+0x190), rejects `Z < SpriteProjForward * -2.0` (constant at 0x10b395fc; not for the ortho RendMap values 13/14/15), projects with `URender::Project` (0x10b2b200), and sizes the quad as `((USize * persp) * DrawScale) * 0.5`. X and Y bounds are `appCeil` of centre minus and plus half size, swapped if needed, clamped to the frame, and rejected when empty. Port: `SpriteSetup` in [`HP1.Core/Runtime/VM/UERenderVisibility.cs`](../HP1.Core/Runtime/VM/UERenderVisibility.cs).
- Open: sprites with `ShowFlags & 0x20` (editor icon sprites) are a loud refusal; they never occur in shipped data.
- Meshes and emitters use the same occlusion walk as sprites (see `frame-tree-and-occlusion.md`); `DrawFrame` names the sprites that were actually drawn and the frontend draws only those.
- Setup order matters for state: `URender::SetupDynamics` goes actor by actor: brush branch, then the sprite `Setup`, then the actor shadow (0x10b2fdb8..0x10b302b2). The master frame is set up first, then the children, then drawing starts. This is observable: an actor shadow's `Update` calls `BonePos`/`ApplyAnim(rootOnly)` and sees the pose header from before the frame's `GetFrame` (D-58).

## DrawFrame order on a device without SpanBased

The retail install selects the Direct3D driver (`RenDev->SpanBased` at +0x48 is 0 for D3DDrv, 1 for the software driver). On such a device `DrawFrame` sorts the frame's sprite array and then makes two passes. Port: [`HP1.Core/Runtime/Render/UESpriteSort.cs`](../HP1.Core/Runtime/Render/UESpriteSort.cs).

- Sort body: `FUN_10b2afa0` (0x10b2afa0..0x10b2b17c), the UE1 `Sort<FDynamicSprite*>` template. A 32-pair (Min, Max) stack; a range of 8 or fewer is selection-sorted (largest by `Compare > 0`, the first maximum wins, swapped to the end); otherwise the middle element goes to Min as pivot, two scans, and the smaller half continues while the larger is pushed (0x10b2b0b1). The sort is unstable, so equal keys keep an order that only this exact algorithm reproduces.
- Compare key: `(a->Actor->Class - b->Actor->Class) / 0x4fc`, an int32 subtraction of two `UClass` object addresses (0x4fc is the class object size), truncated toward zero. In other words the draw order of actors is decided by where their class objects sit in memory, not by distance.
- The original's class addresses vary between runs. A capture of 8000 sorts in the original showed no stable order. NOT ORIGINAL (author decision, 2026-11-03): the port uses the order in which it loads classes (script classes) times 0x4fc, followed by the DLL-native classes ordered by their static class address in Engine.dll. That matched all 8000 logged sorts. This is the only place where the port differs, and only because the original itself is run-dependent.
- Passes (0x10b2666a..0x10b26734): pass 1 draws sprites whose Actor is NULL, or whose Style (+0x155) is not 3 (Translucent) and whose Opacity (+0x194) is at least 1.0. Pass 2 draws everything else. Each pass walks the sorted array in order. A NaN opacity fails the `>= 1.0` test (the original's compare leaves C0 clear for unordered) and goes to pass 2. The frame carries the pass as `ActorSnapshot.LatePass` and the frontend groups by it.
- Sprites are not interleaved into surface list 2. Only the call order between emitters depends on the sort, because it fixes the order of draws from the render random stream.
- A mesh runs `DrawActorSprite` once per frame whose list holds it, with that frame's `FDynamicSprite`; `GetFrame` is not idempotent across draws within a tick (vertex-cache count, tween refill, channel overlay). Port: `DirectRenderStep` in [`HP1.Core/Runtime/VM/UEWorldFrameProducer.cs`](../HP1.Core/Runtime/VM/UEWorldFrameProducer.cs).

## Face order inside one mesh (`DrawLodMesh`)

`URender::DrawLodMesh` (export 0x10b01343, body 0x10b0ff00) sorts a mesh's faces only for some meshes. Port: [`HP1.Core/Runtime/Render/MeshTriangleOrder.cs`](../HP1.Core/Runtime/Render/MeshTriangleOrder.cs); the spec was read from the disassembly, not from the decompile.

- When it runs: on a non-SpanBased device the sort is enabled iff `PolyFlags & 0x10000004` is non-zero, where PolyFlags is the caller's word plus, when `Opacity < 1.0` (also true for NaN), `0x10000004` (0x10b1118a..0x10b111bc). A translucent actor style (PF 4) turns it on; a material with PF_Translucent alone does not, because per-material flags are ORed in later per face.
- Which faces get a key (loop 0x10b11255..0x10b1168d, in face order): faces with level above the LOD vertex count are skipped; a face is accepted when the AND of its three vertex outcodes is 0 and either the face is two-sided or `(N.V0) * Frame->Mirror < 0`, with `N = (V0 - V1) x (V2 - V0)` in frame space.
- Key, owner is not the viewing actor (0x10b11598..0x10b115b6): `(((z0 + z1) + bias) + z2) * 1000`, rounded to int32 (`fistp`, round to nearest even; out of range gives 0x80000000). `bias` is `CollisionHeight * -0.3` when the actor has `bTwoSidedBias` (Actor+0x198 bit 0x40) and the face's material is two-sided, otherwise 0.
- Key, owner is the viewing actor (0x10b115c1..0x10b11673): a hack point H = (0, -8, 0); the key is `(SA * SC) * SB` with each S the squared distance from H to a vertex, computed as `(z*z + y*y) + x*x`. The decompile shows a different product order; the disassembly is the source.
- All of this runs in the x87 24-bit window (`URender::PreRender` calls `appEnableFastMath(1)`), so each step rounds to float. For the viewing actor's mesh a product above 2^31 saturates to 0x80000000, so far faces all tie.
- Sort: `FUN_10b14e40` (0x10b14e40..0x10b14fe2), keys descending (larger = farther), comparisons on the wrapped int32 difference (not plain signed compare, so keys more than 2^31 apart compare inverted), selection sort for 8 or fewer, otherwise quicksort with a 32-entry stack. Not stable.
- Russian edition: the multiplication order differs (`((bias + z2) + z0) + z1`, Render 0x10b10e6f..0x10b10e78 in that build); the port switches on the edition.
- Open: the port transforms the mesh through the Core pose into frame space, while the original transforms straight into the frame in `GetFrame`. Keys can differ by rounding; the order differs only between faces whose depth sums differ by less than 0.001 or tie, i.e. coplanar overlaps.
